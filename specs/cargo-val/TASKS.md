## execution frontier — cargo-val runner

The cargo-val library currently reaches C27/AC113: it parses Cargo JSON and
libtest listing data incrementally, and its dispatch Pipe yields borrowed test
intents as soon as a complete listing line is available, subject to free child
slots. The prior C6/AC68 counted-admission experiment and C7/AC69
retry fixture are rejected as an architecture: they tested a permit pool,
which violates the no-semaphore requirement. Their retained evidence is
historical only. Replacement C6/AC68 adds `SessionSlots`; its observed checks
are recorded in `evidence/c6-slots/acceptance-summary.txt`. The no_std release
binary installs as `cargo-val` and resolves as `cargo val`; help and version
work. Test-run invocations still return status 2 with a not-implemented
message, so the nextest replacement is not usable yet.

The current Proxima process API audit is
`evidence/c28-process-gap/current-api.txt`. It records that process modules are
gated on `std`; `CommandPipe::call` starts a dispatch thread and a separate
reaper thread; direct `Command::output` and `status` drain or wait synchronously;
Unix spawn builds argv and environment vectors before `fork`; and the existing
Windows backend in `spawn_windows.rs` wraps `std::process::Child`, including
blocking `wait` and `wait_with_output`. The source payload is recorded in
`windows-backend-search.txt`. This API does not provide the poll-driven, no_std
child session cargo-val requires. cargo-val must not hide these behaviors
behind an async wrapper. The host adapter below implements only this missing
OS edge and composes it with Proxima's no_std `Pipe` and poll-I/O contracts.

The next cargo-val work completes the pure selection, exact-intent, accounting,
and formatting boundaries, then the fixed-slot host adapter and stream driver.
These consume borrowed data and Proxima Pipes without constructing a suite
queue. The pinned Proxima revision does not expose no_std launch plus
poll-driven stdout, stderr, exit, cancellation, and reaping on all three hosts;
that exact API gap motivates the narrow cargo-val OS edge. Keep the no_std
library and Proxima Pipe/state-machine boundaries; measure allocation sites in
the actual runner before selecting an arena or storage change.

The shipped cargo-val binary and **every normal runtime dependency** must
exclude `std`. A `#![no_std]` marker on the top crate alone is insufficient.
Cargo, build scripts, and test harnesses run on the host and are audited
separately. A cargo-val host session may use a bounded OS launch call;
readiness, stdio, exit, cancellation, and reaping are event-driven thereafter.
No blocking wait/read/write, `block_on`, per-child helper threads, or busy-poll
fallback is admitted. Reuse the existing Proxima Pipe and no_std AsyncRead /
AsyncWrite contracts where applicable; the pinned reactor and process APIs do
not satisfy this runtime boundary. Do not introduce a semaphore, permit, wait
queue, test-name queue, or generic cargo-val process/reactor framework.
The existing pure parser and slot operations are no-alloc; the optional
`proxima-codec` feature and the audited Proxima dependency graph still contain
`alloc` features, so an allocation-free production graph is not established.
The guiding-principle exclusions are concrete: the counted permit experiment
was replaced by directly owned `SessionSlots`; the host adapter stops at the
missing OS edge instead of duplicating Proxima's process API; Proxima `FanIn` owns its
items (`proxima-primitives/src/pipe/fan_in.rs:33-49`), while `DrainFanIn` lends
borrowed items but has no waker (`drain_source.rs:22-29`). Neither merge is a
substitute for a missing async child-event source. Proxima's named `SourcePipe`
requires `Signal` and an erased alloc handle, so it is not the no_std host
source. An arena is deferred until per-child allocation-site traces identify
repeated ownership costs.

states that [anonymous pipes cannot use overlapped I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations),
documents [overlapped named pipes](https://learn.microsoft.com/en-us/windows/desktop/ipc/synchronous-and-overlapped-input-and-output),
and states that [SetThreadpoolWait](https://learn.microsoft.com/en-us/windows/win32/api/threadpoolapiset/nf-threadpoolapiset-setthreadpoolwait)
queues callbacks on a shared worker and cannot outlive its watched handle.
Microsoft documents [PostQueuedCompletionStatus](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-postqueuedcompletionstatus)
for posting the driver's control wake to IOCP.
The Windows callback and cleanup ordering is a candidate until C46b's native
race trace; it is not a proven Proxima or cargo-val API.
